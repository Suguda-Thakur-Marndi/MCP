Production Model Context Protocol (MCP) Server

Enterprise Security Gateway for AI Agents & Real Data

Exposes real PostgreSQL enterprise data to AI clients with strict Human-in-the-Loop approval gating on destructive mutations.

Quickstart Guide View on GitHub Open Approval Console →

1. AI Agents Are Not Security Boundaries

An LLM tricked by adversarial prompt injection will execute destructive actions without hesitation. MCP-Sentinel moves all authorization, risk scoring, and policy enforcement strictly to the authoritative server.

2. Zero Raw SQL & Parameterized Access

No arbitrary query tools (`run_sql` or `execute_sql`). 100% of database access is parameterized via asyncpg against synthetic PostgreSQL tables with strict Pydantic parameter boundaries and projection filtering.

3. Cryptographic Human-in-the-Loop Gating

Destructive actions (`delete_customer`, `purge_inactive_customer_data`) halt closed, returning a SHA-256 parameter-bound ticket. Execution is forbidden until an authenticated human operator authorizes the request out-of-band.

Architecture & Flow

How Human-in-the-Loop Approval Gating Works

A deterministic 5-step lifecycle protecting enterprise databases against autonomous AI mutation, token forgery, parameter tampering, and replay attacks.

1

Agent Invocation

AI client (Claude / Cursor) calls destructive tool: delete_customer(customer_id="CUST-000001", approval_ticket=None).

stdio JSON-RPC
2

Server-Side Gating

SecurityGate evaluates risk (70+, CRITICAL). Server halts mutation, creates pending ticket in PostgreSQL, and returns ticket_id.

Status: REQUIRE_APPROVAL
3

Human Sign-Off

Human operator logs into out-of-band Console, reviews parameters and SHA-256 hash, and approves. Approver identity and HMAC are signed into DB.

Out-of-Band Human Review
4

Bound Execution

Agent retries with ticket. Server verifies HMAC signature & parameter hash, consumes ticket atomically, and executes SQL delete.

Atomic Mutation Executed
5

Anti-Replay Block

Attempting to reuse the consumed ticket is immediately rejected. Ticket status is verified as consumed; zero further changes occur.

Replay Attack Denied
MCP Tool Catalog

Authoritative Tool Specifications

Every tool is defined in mcp_sentinel/server/app.py with strict Pydantic parameter schemas, input length validation, and server-side gating.

Tool What It Does Risk Level Approval Required
query_customer_records Executes parameterized read-only queries with structured allowlisted filters (`status`, `country`, `customer_id`, `tier`). Raw SQL interpolation is strictly forbidden. LOW No
get_customer Retrieves a single synthetic customer profile by integer ID or enterprise code (`CUST-000001`). Returns only approved projection fields. LOW No
get_customer_orders Retrieves purchase order transaction history for a specific customer with bounded pagination (limit/offset). Guarantees data minimization. LOW No
get_order Retrieves a single customer order by internal ID or enterprise order code (`ORD-XXXXXX`). Excludes sensitive system columns. LOW No
append_customer_audit_note Appends an administrative audit note to an existing customer record. Additive operation only; note content is strictly treated as untrusted data. MEDIUM No
update_customer Updates specific customer profile attributes. Strictly restricted to allowlisted fields (`status`, `country`). Arbitrary column updates are prohibited. LOW / CRITICAL Conditional (Mandatory Human Approval for destructive statuses: `suspended`, `closed`, `banned`)
delete_customer Permanently deletes a customer record and associated transactional data from PostgreSQL. High-risk destructive operation. CRITICAL YES (Mandatory Ticket)
purge_inactive_customer_data Permanently purges inactive customer records (by customer_id or bulk inactivity_days retention). High-risk destructive compliance operation. CRITICAL YES (Mandatory Ticket)
Defensive Invariants

Security Model & Guardrails

Defense-in-depth principles implemented directly in the codebase and verified by automated regression tests.

Zero Trust LLM:

The AI model is never trusted as a security boundary; the MCP server independently enforces all authentication, RBAC, and policy checks.

No Raw SQL:

Dynamic SQL execution is strictly prohibited; 100% of database access is parameterized via asyncpg placeholders ($1, $2).

Fail-Closed Execution:

Any validation failure, missing authorization, or expired ticket defaults immediately to denial with typed SentinelError exceptions.

Cryptographic Parameter Binding:

Gating tickets lock execution to a canonical SHA-256 parameter hash, instantly detecting parameter tampering post-approval.

HMAC-Signed Tickets:

Approval tickets are signed with HMAC-SHA256, completely preventing ticket forgery or unauthorized state advancement.

Anti-Replay Locking:

Tickets are consumed atomically via PostgreSQL SELECT ... FOR UPDATE transactions, rendering replay attacks impossible.

Prompt Injection Delimiters:

Retrieved customer notes and fields are wrapped in untrusted data delimiters ([UNTRUSTED_TOOL_DATA]) to isolate prompts.

Append-Only Audit Logs:

Database triggers (trg_audit_events_append_only) raise PostgreSQL exceptions on any UPDATE or DELETE attempt on audit_events.

Error Sanitization:

Internal stack traces, database DSNs, and server paths are stripped; only sanitized safe_message strings are exposed to clients.

Clean Stdio Transport:

All application logging routes strictly to sys.stderr; standard output (sys.stdout) is reserved 100% for JSON-RPC 2.0 frames.

Getting Started

Quickstart: Run MCP-Sentinel Locally

Set up the local PostgreSQL database, apply schema migrations, and boot the FastMCP server in under two minutes.

1. Install Dependencies & Initialize Environment

bash 
# 1. Clone repository
git clone https://github.com/mcp-sentinel/mcp-sentinel.git
cd mcp-sentinel

# 2. Activate virtual environment
python -m venv .venv
source .venv/bin/activate  # On Windows: .venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Copy environment configuration
cp .env.example .env

2. Initialize Database & Seed Synthetic Data

bash 
# Apply SQL schema migrations (001 through 010)
python scripts/init_db.py

# Seed synthetic customer and order records
python scripts/seed_database.py

3. Start MCP Server (Default: stdio JSON-RPC transport)

bash 
python -m mcp_sentinel.server.app

4. Connect Claude Desktop

Add MCP-Sentinel to your claude_desktop_config.json configuration:

claude_desktop_config.json 
{
  "mcpServers": {
    "mcp-sentinel": {
      "command": "C:\\path\\to\\mcp-sentinel\\.venv\\Scripts\\python.exe",
      "args": [
        "-m",
        "mcp_sentinel.server.app"
      ],
      "cwd": "C:\\path\\to\\mcp-sentinel",
      "env": {
        "DATABASE_URL": "postgresql://postgres:postgres@localhost:5432/mcp_sentinel_db",
        "APP_ENV": "development",
        "LOG_LEVEL": "INFO"
      }
    }
  }
}

5. Connect Cursor IDE

Add MCP-Sentinel to .cursor/mcp.json in your project root:

.cursor/mcp.json 
{
  "mcpServers": {
    "mcp-sentinel": {
      "command": "C:\\path\\to\\mcp-sentinel\\.venv\\Scripts\\python.exe",
      "args": [

        "mcp_sentinel.server.app"
      ],

      "env": {

        "APP_ENV": "development",
        "LOG_LEVEL": "INFO"
      }
    }
  }
}
